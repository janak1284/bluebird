PS-S04 Multi-Objective Dynamic Workload OrchestratorBuild Blueprint v2 — 4 Linux Laptops · 4 People · 24 HoursThis document is written to be understood, not just followed. Every instruction comes with the reason behind it, because at 3am you will hit something this document did not anticipate, and reasons travel further than instructions do.Read sections 1 to 4 as a team before anyone writes code. The rest can be read by whoever owns that piece.1. Understand the Problem FirstThe one tension everything comes fromAn edge node is a small machine physically close to users. A round trip to it takes about 3 milliseconds. But it is a tiny box in an inconvenient location, so compute on it is expensive — you are paying for underused hardware someone has to maintain.A core data centre is a warehouse of servers far away. A round trip takes about 40 milliseconds, because of physics and network hops. But compute there is cheap: bulk electricity, bulk cooling, machines kept busy.So: edge is fast and expensive, core is slow and cheap. That single sentence generates the entire problem statement. Every requirement in the PS is a consequence of it.Why static placement failsSuppose you deploy an app to an edge node and leave it there. At 6pm everyone finishes work, traffic multiplies tenfold, the edge node runs out of CPU, requests queue, and latency climbs past whatever you promised. The promise — the SLA — is broken.The obvious fix is to run everything in the core instead. Infinite capacity, never overloaded. But now every user pays 40ms permanently, so the promise is broken a different way, and you are burning power hauling traffic across the country that never needed to travel.Neither fixed choice works, because the right answer changes minute to minute. The system has to decide continuously. That continuous decision-maker is what you are building.What you are building, preciselyA control plane: a program that watches a set of machines with different cost, latency and power characteristics, and repeatedly decides which machine each containerized workload should run on — then moves it there without users noticing.KEEP THIS IN VIEW  You are not building the applications. You are building the thing that places applications. The placement decision is the intellectual centre of the project; telemetry, migration and the dashboard exist to feed it, carry out its decisions, and make them visible. Budget your 24 hours accordingly.The loop it runs, foreverMonitor — collect node capacity, live CPU and memory use, measured p99 latency per workload, and node health.Analyze — is any SLA breached, or about to be? Which workloads are candidates to relocate?Plan — score every possible placement across several competing objectives, find the set that is not beaten on every axis, and pick from it under an explicit policy.Execute — move the workload without dropping requests: start the replacement first, wait for it to be healthy, then retire the original.Remember — keep placement history, so the cost of moving and a minimum settling time can be taken into account next cycle.2. The Three Behaviors That Win ThisA weak version of this project reacts to overload one way: shove things to the core. That is a threshold with extra steps, and judges recognise it immediately.A strong version exhibits three distinct behaviors — and crucially, you do not program the three behaviors separately. They all fall out of one objective function. That is the whole argument for multi-objective optimization over hand-tuned rules, and it is the thing to say out loud in your pitch.Behavior A — Peer balancing (edge to edge)Edge-1 is saturating. Edge-2 has spare capacity. Compare the two candidate moves:MoveLatencyCostVerdictedge-1 → edge-2stays ~3 msunchanged (both edge)Better on latency, equal on cost — it dominatesedge-1 → core-1jumps to ~40 msmuch cheaperWorse on latency, better on cost — a real tradeoffWhen edge-2 has room, the peer move is better on latency and no worse on cost, so it dominates the offload option and the optimizer picks it automatically. You never write "try balancing first." It emerges. Say exactly this to the judges — it is a far stronger claim than describing a fallback hierarchy you coded by hand.Behavior B — Offload (edge to core)Now surge both edge nodes. No peer has capacity, so the peer move is no longer available. The only remaining options are: stay put and breach the SLA through queuing delay, or accept the core's 40ms and survive.This is where the genuine tradeoff appears, and where the Pareto front becomes visible on your dashboard — several non-dominated options, none strictly best, one chosen by an explicit policy.Behavior C — Consolidation (quiet hours)When traffic is light, packing everything onto one core node and letting the edge machines idle is best on cost and best on power, with no SLA risk. It costs you nothing to implement — it is simply what the optimizer returns when demand is low.Worth doing because it shows the system optimizing in the quiet direction, not only firefighting. Most teams only demo the panic case.THE PITCH SENTENCE  "We did not implement load balancing, offloading and consolidation as three features. We implemented one objective function, and all three behaviors emerge from it depending on which placements happen to be non-dominated at that moment."Two design choices these behaviors require1. Workloads must have different latency tolerancesIf every workload demands 20ms, core placement is never feasible — 40ms of base latency breaches it before any work is done — and Behavior B becomes impossible to demonstrate. So give workloads classes:workloads:  checkout:   {class: latency-critical, sla_ms: 20}   # edge only  recommend:  {class: standard,         sla_ms: 80}   # either  analytics:  {class: batch,            sla_ms: 500}  # core is fineThis unlocks the smartest behavior in the whole system: under pressure, the optimizer evicts the batch job to core to free edge capacity for the latency-critical one. It moves the right workload, not the overloaded one. Judges notice this.2. Your two edge nodes must not be identicalGive them different core counts, or base latencies of 3ms and 4ms. If they are identical, every edge-to-edge swap ties on every objective, your Pareto front fills with duplicate points, and the tiebreak logic has nothing meaningful to do. A little asymmetry makes the front real.3. Cluster TopologyCHANGED FROM THE EARLIER PLAN  All four laptops are now cluster nodes. You are modelling economics you do not physically have, which is completely legitimate — but say so plainly rather than implying these numbers are measured.nodes:  laptop-1: {tier: core, base_latency_ms: 40, cost_per_hr: 2.0,             idle_w: 25, max_w: 65, cpu_cores: 8}  laptop-2: {tier: edge, base_latency_ms: 3,  cost_per_hr: 9.0,             idle_w: 12, max_w: 45, cpu_cores: 4}  laptop-3: {tier: edge, base_latency_ms: 4,  cost_per_hr: 9.0,             idle_w: 12, max_w: 45, cpu_cores: 2}   # deliberately weaker  laptop-4: {tier: core, base_latency_ms: 38, cost_per_hr: 2.2,             idle_w: 25, max_w: 65, cpu_cores: 8}Power model: power_w = idle_w + (max_w − idle_w) × cpu_utilization. You cannot measure a laptop's wattage in software. This linear curve is what capacity planners actually use, so it is defensible — as long as you call it a model. If a laptop is on battery, /sys/class/power_supply/BAT0/power_now gives you one genuinely measured node, which is a nice detail to mention.5. The Optimizer — Where You Win or LoseWhy a weighted sum is not good enoughThe tempting approach is score = w1·latency + w2·cost + w3·power, pick the lowest. Almost every team will do this. Two problems.First, it hides the tradeoff. Collapsing four numbers into one throws away the information that made the decision interesting, and when a judge asks "why this placement and not that one?" your only answer is "the weights said so."Second, the weights are arbitrary. You picked them. A different set gives a different answer and you have no principled defence of yours.Multi-objective optimization keeps the objectives separate. Instead of one winner it produces a set of placements where no member is beaten by another on every single objective at once — the Pareto front. Selecting from that set is then a stated policy decision, not a hidden weight.Dominance, in one examplePlacement A: 8ms latency, ₹100/hr. Placement B: 18ms latency, ₹40/hr. Neither dominates — A wins on latency, B wins on cost. Both belong on the front. Placement C: 20ms, ₹120/hr is beaten by both, so it is discarded.You can put exactly this on the dashboard and point at it during the demo. That is the moment that separates you from the weighted-sum teams.The four objectivesSLA risk — projected p99 latency against the workload's declared bound. Projected latency = node base latency + a queuing estimate derived from projected utilization. Queuing is the important half: an overloaded node adds far more delay than distance does.Cost — sum of cost_per_hr across nodes carrying load under this candidate placement.Power — sum of modelled watts under this candidate placement.Migration cost — how many workloads would have to move relative to where things are right now, weighted by workload size.THE FOURTH OBJECTIVE IS THE ONE PEOPLE FORGET  Most teams treat moving a workload as free. It is not: it costs downtime risk, state transfer and bandwidth. If your optimizer does not price it, it will flip workloads back and forth every cycle as metrics jitter — thrashing — and it will do it live, in front of judges. Pricing migration gives you hysteresis for free.The algorithmEnumerate candidate placements. With 4 nodes and a handful of workloads, exhaustive enumeration is tractable and much easier to defend in a viva than a heuristic search. Use beam search only if the space grows.Discard candidates that violate hard constraints: node capacity exceeded, node not Ready, workload class forbids that tier.Compute the four-element objective vector for each surviving candidate.Extract the non-dominated set — the Pareto front. A candidate is dominated if some other candidate is at least as good on all four objectives and strictly better on at least one.Select from the front using the active policy. Lexicographic works well and is easy to explain: never breach SLA, then minimise cost, then power. Break remaining ties by crowding distance so you prefer well-spread solutions over clustered ones.Stopping thrash — both mechanisms, not oneMigration cost as an objective, so a move has to justify itself against the disruption it causes.Minimum dwell time (around 30 seconds) as a hard constraint — a workload that just moved cannot move again until it expires. This is a floor, in case the objective weighting is not enough.Demo value: run once with migration cost switched off to show the thrashing, then switch it on and show the system settle. A thirty-second beat that proves you understood something the problem statement never said.6. Making Placement Happen — a Custom SchedulerCHANGED FROM THE EARLIER PLAN  The earlier plan used kubectl patch deployment to change a nodeSelector. That works, but it means Kubernetes' own scheduler makes the final placement inside your constraint — so your optimizer degenerates into a threshold that flips a label. Bind pods yourself instead. Same optimizer, categorically stronger claim.Mark your workloads with a scheduler name that does not exist. The default scheduler then ignores them completely, and they sit in Pending until you decide where they go.spec:  schedulerName: pareto-scheduler  terminationGracePeriodSeconds: 20  containers:  - name: app    image: workload:local    imagePullPolicy: IfNotPresent    readinessProbe:      httpGet: {path: /healthz, port: 8080}      periodSeconds: 1      initialDelaySeconds: 0Your controller watches for pending pods, runs the optimizer, and issues a Binding — the same API call the real scheduler makes:from kubernetes import client, configconfig.load_kube_config()v1 = client.CoreV1Api()def bind(pod_name, node_name, ns='default'):    body = client.V1Binding(        metadata=client.V1ObjectMeta(name=pod_name),        target=client.V1ObjectReference(kind='Node', name=node_name))    v1.create_namespaced_binding(        namespace=ns, body=body, _preload_content=False)GOTCHA THAT COSTS TEAMS AN HOUR  _preload_content=False is required. Without it the Python client tries to deserialize the response as a V1Binding object and raises an exception — even though the bind actually succeeded. You will chase a phantom bug.7. Migration — There Is No Migrate ButtonWhy notA pod's node assignment is fixed the moment it is bound and cannot be changed. This is deliberate: Kubernetes treats pods as disposable. If you want a workload elsewhere, you create a new pod there and destroy the old one. So migration is a sequence you orchestrate, not a call you make.The naive version — delete the pod and let the Deployment recreate it — drops every request for 3 to 8 seconds while the replacement starts. That directly contradicts any near-zero-downtime claim you plan to make.Make before breakRecord the current pod's name, so you can tell the old one from the new one later.Scale the Deployment from 1 replica to 2. A new pod appears in Pending.Identify the new pod by diffing against the recorded name, and bind it to the target node.Poll until its Ready condition is true. This is the critical gate: a Service only routes traffic to Ready pods, so until this instant the original is still serving 100% of requests.Both pods now serve traffic. This overlap window is the entire reason downtime is zero.Delete the original pod by name, then scale back to 1.ORDER MATTERS  Delete the specific old pod before scaling down. If you scale down first, the ReplicaSet controller chooses which pod dies — and it may well choose the new one you just carefully placed.Rerouting: you do not have to do anythingA Service is a stable virtual IP and DNS name in front of your pods. As pods appear and vanish, kube-proxy rewrites the underlying iptables rules automatically. The pod's IP changes on migration; the Service address never does. Clients address the Service forever and your controller never touches routing.apiVersion: v1kind: Servicemetadata: {name: checkout}spec:  selector: {app: checkout}  ports: [{port: 8080}]Making it fast enough to look goodPre-pull every image onto all four laptops before judging. A cold image pull over a phone hotspot takes 30 seconds or more and will destroy the demo.Use a tiny image. A Go or Python HTTP server on Alpine starts in under a second. Anything JVM-based takes 10+ seconds and makes your migration look broken.Handle SIGTERM in the app: stop accepting new connections, finish in-flight requests, exit. Without this, requests in flight when the old pod dies will fail, and your zero-error claim collapses.With all three, expect 1 to 3 seconds of cutover with zero dropped requests. Measure it and report the actual number — a measured claim beats an asserted one every time.8. StateCHANGED FROM THE EARLIER PLAN  Firebase/Supabase put an internet dependency directly in your demo path, over a phone hotspot, in a room full of judges' devices competing for the same access point. Run Redis as a pod pinned to a core node instead: local, fast, no internet — and architecturally more correct, since real edge-core systems co-locate state with core.Do not attempt CRIU memory checkpointing. It freezes a running container's memory to disk, ships it, and restores it elsewhere. It is alpha in Kubernetes, runtime-specific, and it will consume your entire hackathon. This is the single biggest trap in this problem statement.State externalization is how production systems genuinely solve this, so saying so is a stronger position than a fragile checkpoint demo — not an excuse.Optional, if you have spare hours: application-level handoffIf you want to visibly show state moving, do it in your app rather than the kernel. Two endpoints: GET /state/export returns in-memory data as JSON, POST /state/import loads it. The controller sequences export, import, readiness flip, drain. About two hours of work, entirely under your control, and it demos beautifully — an in-memory counter survives a migration between physical laptops.9. The Staged DemoWHY STAGED  A single migration looks like a threshold firing. An escalation — cheap fix first, expensive fix only when forced, then recovery — shows the system reasoning about which move to make. That escalation is the pitch.Establish the geography. Point at the four physical laptops. "These two are edge sites — 3ms away, expensive. These two are the core data centre — 40ms away, cheap. That latency is injected at the kernel level with tc netem; it is real network delay, not a number in our code."Show steady state. Dashboard: checkout on edge-1 at 12ms against a 20ms bound, analytics on edge-2, load generator showing zero errors.Show the Pareto front. "Right now there are three non-dominated placements. Here is what each trades away, and here is the policy that chose between them." This is the moment that separates you from every weighted-sum team in the room.Surge one edge node. Ramp load on edge-1. CPU climbs, queuing delay grows, p99 crosses 20ms.BEHAVIOR A — peer balancing. The system moves a workload edge-1 → edge-2. Explanation line: peer edge has headroom, so relocating preserves 3ms latency at no cost change. "Notice it did not go to the core. It found the cheaper fix on its own — we never coded that preference."Surge the second edge node too. Now no edge node has capacity anywhere in the cluster.BEHAVIOR B — offload with class awareness. The system moves analytics (batch, 500ms tolerance) to core, freeing edge capacity for checkout. "It moved the batch job, not the one that was struggling. That is the multi-objective engine deciding what to sacrifice."Drop the load. After dwell time expires, workloads migrate back to edge and latency recovers. "This is a control loop, not a one-way threshold."BEHAVIOR C — consolidation. Let load stay low. The system packs workloads onto one core node and lets edge machines idle, cutting cost and power with no SLA risk.Chaos. Close an edge laptop's lid. Node goes NotReady in about 20 seconds and its workloads redistribute automatically.The proof. Ablation table. "Same traffic trace, four policies. Ours: zero SLA violations at 38% lower cost than all-edge."Backup planRecord a screen capture of a successful full run at hour 21. If anything fails live, narrate over the recording. Every experienced team does this and no judge holds it against you.16. What to Claim, and What Not ToCredibility is one number.
